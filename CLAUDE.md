# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repository contains `index.html`: a single-file, dependency-free Kanban board web app ("ABC IT PMO — Kanban Board") — a demo/training tool, not a production system tied to any real bank system or branding. There is no build tooling, package manager, test runner, or server component in this repo.

## Running the app

There is no build step and nothing to install. Open `index.html` directly in a browser (double-click it, or `open index.html` / `xdg-open index.html`). There are no lint or test commands configured in this repository.

**Deployment**: `.github/workflows/deploy-pages.yml` publishes to GitHub Pages on every push to `master` (or manual dispatch). It copies only `index.html` into `_site/`, so any additional file would not be deployed — another reason to keep everything in one file.

## Hard constraints for this file

These constraints are load-bearing for the app's design — preserve them when making changes:

- **Vanilla only**: plain HTML, CSS, and JavaScript. No frameworks (React/Vue/jQuery/Tailwind), no build step, no bundler, no npm dependencies.
- **Single file**: all markup, the `<style>` block, and the `<script>` block live in `index.html`. Do not split into separate `.css`/`.js` files — it must keep working when opened directly from disk with no server.
- **No persistence**: board data lives only in the in-memory `state` object. Do not introduce `localStorage`, `sessionStorage`, `IndexedDB`, cookies, or any other storage API — a page refresh resetting to seed data is intentional behavior (see the "Demo mode" note in the header).
- **No external resources**: no CDN scripts, no Google Fonts, no external images. Icons are inline SVG or Unicode glyphs; fonts come from the system font stack (`--font-stack` custom property).
- **Notifications only via FormSubmit**: the only network call is a `fetch` to the FormSubmit AJAX JSON endpoint (`FORMSUBMIT_ENDPOINT` constant near the top of the `<script>` block). It must never block or break the UI — see Architecture below.

## Architecture (all inside `index.html`)

**Single source of truth**: a module-level `state` object (`{ tasks, filters, taskIdCounter, pendingDeleteId }`). All rendering derives from `state`; there is no direct DOM mutation of card contents outside `renderBoard()`/`renderCard()`/`renderColumn()`.

**Render flow**: any mutation (`addTask`, `moveTask`, `deleteTask`, `applyFilters`) updates `state` and then calls `renderBoard()`, which rebuilds the four columns' HTML from `getFilteredTasks()` and re-attaches event listeners via `attachBoardEventListeners()` (event delegation is re-wired every render since the DOM is regenerated each time).

**Optimistic add-task flow**: `addTask()` pushes into `state.tasks` and re-renders synchronously; `notifyNewTask()` (the FormSubmit call) is fired afterward. The submit handler awaits it only to keep the submit button disabled in its "Sending…" state; the form is already reset and the card already shown by then, and the modal closes once it settles. Its `try/catch` swallows network failures and only shows a warning toast (`showToast(..., "warning")`) — a failed notification must never remove the card or block the board. Task IDs are generated by `nextTaskId()` in the format `ABC-ITPM-####` from a monotonically incrementing `state.taskIdCounter` (not from array length, so IDs stay unique after deletes).

**Drag-and-drop + keyboard fallback**: cards are `draggable="true"` with native `dragstart`/`dragover`/`drop` handlers wired per-render in `attachBoardEventListeners()`; the same state change (`moveTask(id, newStatus)`) is also reachable via the per-card "Move" `<select>` for keyboard/non-mouse use. Both paths converge on `moveTask()`.

**Delete confirmation**: inline, not `confirm()`. `state.pendingDeleteId` tracks which single card is showing its Yes/No toggle; `renderCard()` reads it to decide whether to render the confirm block for that card.

**Security**: all user-supplied strings are passed through `escapeHtml()` before being interpolated into template strings that become `innerHTML`. Preserve this on any new field that renders user input.

**Filtering**: `applyFilters()` reads the three filter controls (project, assignee substring, priority) into `state.filters`; `getFilteredTasks()` is the single filter predicate used by rendering — keep filtering client-side and pure over `state.tasks`.

## FormSubmit integration notes

- `FORMSUBMIT_ENDPOINT` is the one constant to change when repointing notifications to a different email address.
- FormSubmit requires one-time activation: the first submission to a new address triggers a confirmation email, and no notifications deliver until that link is clicked. This is documented in an HTML comment directly above the constant — keep that comment if you touch this section.
- Never send the user's real email address (or any other PII) to any endpoint other than `FORMSUBMIT_ENDPOINT`.
